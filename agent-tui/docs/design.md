# agent TUI design

Distilled from two research briefs (interaction, visual) on lazygit, helix, k9s, yazi, zellij, tmux, gitui, television and atuin. Owner decisions override the briefs where they conflict, and are marked **(owner)**. Every visual or interaction change is reviewed against this doc by adversarial design reviewers.

## Principles

1. **One hint line, chosen by context. The full map lives behind `?`.** lazygit's `showBottomLine`, k9s's per-view menu, gitui's "context based help". Never a static hint block in a sidebar.
2. **The mode is stated in text, not only colour.** helix `NOR`/`INS`, zellij's status bar. We have two modes: `AGENT` (keys go to the pty) and `NAV` (keys go to the app).
3. **Entering AGENT is always intentional.** Only `⏎` and `i` (and `⏎` or `i` in a peek, or on a `move here` row) put the keys in the pty. Nothing else enters it as a side effect, except an agent chord pressed while the keys are already in AGENT (see Always-on chords): not `0`, `Esc`, `a`, the switcher, a mouse click, a launch landing or the nav key. Leaving AGENT is a deliberate act and landing in it when NAV was expected is jarring. `nav` (default `Ctrl+]`, configurable under `[keys]` so a harness or terminal that claims it can be worked around, and any key a terminal can send on its own: `ctrl-<letter>`, `ctrl-space`, `ctrl-\ ctrl-] ctrl-^ ctrl-_`, `alt-<char>`, `f1`-`f12`) leaves AGENT for NAV on that agent. Pressed again within two seconds, with no other key or mouse event between and only when the first press was the configured nav key (not the escape hatch), it selects and previews the agent used before (tmux `last-window`, without entering it). Pressed in NAV after any other key it does nothing. What `⏎` or `i` asks for is carried by the pane until the connection exists, across the check for other windows and across a launch, and is dropped to a preview unless the user is still on that agent's row with the keys in the same panel and no overlay or peek open, and a later `0`, `a`, switcher pick or nav-nav on that agent also makes it a preview. A launch from the form or a checkout always previews and says `<agent> is ready · ⏎ enters`. The owner tried a one-shot mode plus a second sustained key, like AeroSpace's, and dropped it: no second Ctrl chord was easier to reach than the first. The always-on agent chords are not that: they are not Ctrl chords, they don't leave AGENT or hold a mode, they are optional (`none` turns them off) and they are configured through the same key specs as `nav`.
4. **Leaving is free to undo.** `⏎` or `i` on the agent you left enters it again.
5. **Attention is a per-agent flag plus a jump key** (tmux `#`/`!` flags, `next-window -a`). Source: hooks the harness is launched with (Claude: `--settings` carrying `UserPromptSubmit`, `PreToolUse`/`PostToolUse`, `PermissionRequest`, `Stop`, `StopFailure`, `SessionEnd`), reported through `agent event` into the state dir. `idle_prompt` is ignored because it fires while background work still runs.
6. **Confirmation strength matches what is lost.** One vocabulary: `y` confirms, `Y` confirms data loss, `Esc`/`n` cancels.
7. **Respect the user's palette.** Colours are roles, and each defaults to a named ANSI colour: accent Cyan, warning Yellow, error Red, success Green. This doc names them by their defaults. `Color::Reset` backgrounds. Secondary text (DIM in this doc) is the terminal's foreground blended into its background, read with `OSC 10`/`OSC 11` at startup before the input thread reads the tty. The blend starts halfway and takes more foreground until it reaches 3:1 contrast with the background, since halfway is barely readable on light themes and Solarized. It falls back to the `DIM` attribute when `COLORTERM` doesn't promise 24-bit colour or the terminal doesn't answer within a second (locally it answers in milliseconds, and the wait ends there). It is read once, so a theme change needs a restart. Never `DarkGray`, because brblack is the background in Solarized. `[theme]` (owner) overrides any role with an ANSI name, `#rrggbb` or `default`, and `dim` also takes `faint`. `NO_COLOR` drops every colour.
8. **Selection never depends on span colours.** No `REVERSED`, no background fill: a 1-column `▌` gutter (Cyan when the list has focus, DIM otherwise) plus a BOLD name.
9. **Whitespace and single rules over boxes.** Boxes only for overlays.
10. **Colour encodes state and is never alone**: every state has a distinct glyph, so it reads with `NO_COLOR` or a monochrome theme. No Nerd Font dependency.

## Layout (owner: lazygit-style panels, modern status bar)

```
╭ [1] heucristic ───────────╮╭ [0] heucristic / triage-flow ───────────────────╮
│▌◆ triage-flow           1 ││ <embedded terminal>                             │
│ ● payroll-fix             ││                                                 │
│ ✓ main                    ││                                                 │
╰─────────────────── 1 of 3─╯╰─────────────────────── ~/worktrees/heucristic/… ╯
  NAV    ⏎ enter  Space switch  d kill  D remove  m pin  ] agents  ? keys      killed foo
```

- Rounded panels, like lazygit: the sidebar's three (see Sidebar) and the main view [0], which shows the selected agent's terminal or what a panel's cursor is on (see Main view). Each has its title in the top border and its metadata in the bottom-right corner (`N of M` for the list, the path for the terminal, or a Yellow `⇄ in nvim` (naming the place, see Open elsewhere) while the keys are in an agent another window shows too).
- The panel keys go to has a Cyan border (the focused sidebar panel in NAV, a focused document in [0], the terminal in AGENT). The others are DIM, and all are DIM while an overlay has the keys. The owner rejected free-floating rules and a titles-in-rules frame. Borders belong to panels.
- Sidebar: 24% of the width, clamped to 28-48 inner columns, plus its border. It's hidden below 60 columns so the agent keeps every column (Space still switches). Rows keep one column of inner padding on both edges. The terminal panel has one column of horizontal padding so the agent's own full-width rules don't fuse with our border.
- List title: `[1]` then the three tabs, lazygit-style: `Agents`, the selected row's repo (`heucristic`) and `Pinned`, the active one BOLD and the others plain with a DIM ` · ` between. The form follows the width alone, never the cursor: below 32 columns inside the border (the title's two padding columns, 4 for `[1] `, 8 for the shortest repo name, 18 for the other tabs) only the active tab shows, and above it the repo name yields to fit as names do. With the sidebar clamped to 28-48 inner columns that means the strip shows from about 140 columns. With no row selected only the active tab shows, and the repo tab with no repo is bare `[1]`. Position lives only in the `N of M` corner, in the border's colour and tucked against it (`1 of 3─╯`). The focused panel's title takes the Cyan accent, as lazygit's active title does. Terminal title: `[0]` then the identifier BOLD (Cyan when focused): `repo / agent` with the repo and `/` DIM, or for a main checkout `repo` BOLD + ` branch` DIM.
- Status bar (one row, no border, the owner's "modern neovim-ish bottom nav"): the mode badge (`  NAV  ` / ` AGENT `, seven columns, accent reversed. The accent always means "keys go here", and warning is reserved for attention and warnings), then the context's hints (key default fg, description DIM), then the status message right-aligned (errors Red and sticky until the next key, warnings in the warning colour that survive keys and expire after ~30s, info expiring after ~4s). The hints are not capped. Each binding in the table in `crates/tui/src/keymap.rs` carries a rank, which may depend on the focused panel, the hovered item and the mode, and the bar shows as many as fit the width, dropping the lowest ranked first (at most widths that is `x`, `e`, `D`, `.`, `d`, `m`, then `Space` outside [1], `n`, `v`, `s`, `]`; `h l` are Hidden in the table, so they're never in the footer), while `? keys` stays. The same table feeds the help, so the two can't disagree, and a hint is never shown twice. The status is cut to fit rather than pushing hints out, so the row never jitters. In AGENT the hints are `⌃] nav  ⌃] ⌃] previous  ⌥, ⌥. agents` with the defaults, naming the configured keys, leaving out a chord that is off (plus the attention count once status exists). In NAV the chords' hint is `⌥, ⌥. agents` where [1] has the keys, ranked below `n new`, so it is the first to go on a narrow bar. The peek's badge reads ` PEEK `. Hints never offer actions that are invalid for the selection.
- The nav key is parsed once into a `KeySpec` and matched on its exact modifiers. Keys a terminal sends on its own are `ctrl-<letter>` (not `h i j m`), `ctrl-space`, `ctrl-\ ctrl-] ctrl-^ ctrl-_`, `alt-<char>` (not `alt-[` or `alt-O`, which start escape sequences) and `f1`-`f12`. Keys that only the kitty keyboard protocol can send are `ctrl-shift-<letter>`, `super-<char>` (the Cmd key on macOS, always shown `⌘`), `ctrl-h ctrl-i ctrl-j ctrl-m ctrl-[`, `alt-[` and `alt-O`. A spec is refused when it has no modifier (`esc`, `tab`, `x`), is `esc esc`, or duplicates another configured key, and a chord can't be `ctrl-]` while the nav key isn't a control key, since `⌃]` then also leaves AGENT. `prev_agent` and `next_agent` also take `none` or `off`, parsed to `Binding::Off` rather than an empty key, and `nav` can't be off. At startup a key the terminal can't send is replaced by its default (`⌃]` for nav, `⌥,` and `⌥.` for the chords, or left off when another configured key already has that default), and a warning says so (`keys.nav ⌃⇧T is not available in this terminal, using ⌃]`) in the status bar and under `Keys` in the help. It outlives keypresses and expires after 30 seconds, and any other message replaces it, so no feedback is lost. The fallback stays listed in the help. A shift is part of the key: `alt-<`, `alt-?`, `ctrl-^` and `ctrl-_` match however the terminal reports the shifted character (a US keyboard's shift pairs are assumed). On a legacy terminal Ctrl+4 to Ctrl+7 are the same bytes as `ctrl-\ ctrl-] ctrl-^ ctrl-_`, and Ctrl+2 or Ctrl+@ the same as `ctrl-space`, so they can't be told apart. A nav key that isn't one of those control keys (`alt-`, `f`, kitty-only) might be swallowed by the terminal (a new-tab shortcut, Option composing `≈`) with no way back, so `⌃]` also leaves AGENT then, shown as `⌃] also leaves` in the AGENT footer and in the help. A control nav key has no second key, so `nav = "ctrl-\\"` leaves `⌃]` to the agent. The default changed from `⌃\` to `⌃]`: a config that doesn't set `nav` now sends `⌃\` to the agent, and `nav = "ctrl-\\"` keeps the old key.
- Key names, everywhere (status bar, overlays, help): `⏎`, `Esc`, `Space`, `Tab`, and the configured escape key (the nav key), shown as `⌃]`, `⌥,`, `F12` or `⌃Space`, or `⌃⇧J` and `⌘j` (a `super-` key) for the keys that need the kitty keyboard protocol. The vocabulary is one verb per action: **attach** (the keys go to the agent's terminal), **send** (compose a message, typed at once or refused), **open** (focus [0] on the item), **peek**, **nav** (the exit key and its mode) and **back** (one level out).
- Render the pty cursor only in AGENT.

## Glyphs

| state | glyph | style |
|---|---|---|
| asking (a permission prompt or a question) | `◆` | Yellow BOLD, name BOLD, time Yellow |
| failed (rate limited, overloaded…) | `!` | Red BOLD, name BOLD |
| done, unseen | `✓` | Green BOLD, name BOLD |
| working, or its activity ended while background subagents run | braille spinner, `↳n` (DIM) after the name while subagents run and line 2 doesn't say so | default |
| working but silent for 5 minutes with no tool running | the frozen frame, time with a Yellow `?` | default |
| launched through `agent` and nothing reported yet (at most 30 seconds), or the harness reported its session starting less than 5 seconds ago | braille spinner, line 2 `starting` | default |
| interrupted: the user stopped the activity and nothing has followed | `■` | DIM, name default, time DIM |
| idle, seen, or a harness without hooks | `●` | default |
| exited (resurrectable) | `○` | DIM, name DIM |
| no session | `·` | DIM, name DIM |
| background commands the agent has running (`⌁`, U+2301), in any live state. It never changes the glyph, the state, the tier, Needs you or the counts | `⌁n` (DIM) after the name, after `↳n` when both show, and not when line 2 names the commands. The activity's status row counts them too (`↳2 · ⌁1`) | DIM |
| open in another window (a terminal tab, an editor, SSH, tmux), on any card, not only the selected one | `⇄` in the right column | DIM |
| open in another window while the TUI types into it | `⇄` in the right column | Yellow |
| a file another agent changed too | `∩` before its counts in [3] | Yellow |

`⌁` is a single cell in WezTerm's font chain (`wezterm ls-fonts --text '⌁'` resolves it through the system fallback, Menlo, at the same advance as JetBrainsMono NF), so it needs no Nerd Font glyph. A background command is something the agent started and isn't waiting on, often a server or a watcher that never ends, so commands annotate a state and never make one: a finished activity stays `✓ done` while its commands run, and an idle agent stays `●`. They are drawn only for an agent with a live session, since a crash leaves its last listing behind.

Never `✗`/`×` for exited (reads as "close"). Rows show the time in state right-aligned (`38s` `4m` `2h` `3d`) for working, asking, failed, done and interrupted, and since the activity ended for delegating. Green means only `✓` and added lines.

## Attention

- Overview opens with a **Needs you** group listing every asking, failed or done-unseen agent, in the order `a` visits them: asking and failed first, then done, longest waiting first. A waiting agent shows here and nowhere else, not under its repo. Pinned ends with the same group for the waiting agents that aren't pinned. Selecting a row here keeps no repo open for it, so when repos don't all fit they close from the bottom. Collapsed repo counts leave waiting agents out.
- Focus lists agents from other repos that need you under the repo's cards, in a `▾ Needs you` group with their repo on the right. They're one line each and can't be selected, since selecting one would change the repo in focus: `a` goes there. The status bar carries the counts.
- `a` selects the most urgent agent other than the one whose terminal [0] shows and previews it in NAV, saying `<agent> needs you · ⏎ enters`. With none: `Nothing needs you`.
- Done clears to idle on attach, or after 3s with its terminal visible in [0] while the terminal has focus (terminals that never report focus count as focused). Reading its diff or its activity in [0] doesn't clear it. Failed clears on the next prompt, asking when its hook state changes.
- Status bar: at the far right, `a ◆ n  ! n  ✓ n` , never cut, hidden at zero. It counts what `a` would visit, so the agent being typed into isn't counted. It shows and hides as one block at the edge, so the hints never shift. The terminal title (OSC 2) carries the same counts first: `◆2 ✓1 · agent`.
- One bell when an agent other than the one being typed into starts asking, fails, or finishes an activity of 30s or more. At most one per 10s.

Three panels stacked, each a plain list that picks what [0] shows: [1] the fleet, [2] the selected agent's activity and subagents, [3] its work in git. `1` `2` `3` focus them (see Keymap). The prose lives in [0], where there is room for it. The layout is a function of content and selection alone, and focus never moves a panel's edges. Selecting another agent, or a panel that isn't shown, puts the focus back on [1]. The focused panel takes the Cyan border and title while the sidebar has the keys, and the others are DIM. Below an inner width of 36 the short forms apply.

- [1] is sized to its rows, at most what leaves [2] and [3] their minimums (4 rows for [2], and 3 file rows plus the readiness row for [3], inside their borders), and scrolls past that. That reserve binds only [1]'s room, so the selection never changes it. Its corner shows `N of M`, counting the agents Focus lists from other repos.
- [2] is sized to its rows, up to 6, and [3] takes the rest. Neither vanishes while an agent is selected: each has a title and at least one row, which says why when it has nothing to list. Only when the column is too short for [2]'s floor (3 rows) and [3]'s least (a title, the readiness row and three files, or what it has of them) does [2] take everything and [3] go, and the `3` key says so. With no agent selected (a repo row), [1] takes the whole column. A list that has the keys scrolls to keep its cursor in view. Unfocused, [3] ends with `+k more` when its rows don't all fit.

### Cards

```
▌◆ triage-flow                   heucristic  4m
▌  Bash: pnpm test --filter triage
```

- Line 1: gutter, glyph, name, then on the right the repo (DIM, only in Needs you and the Pinned tab, and not in the short form), the time in state and `⇄`. The right side never truncates, and the name yields down to 8 columns.
- Cards under a `▾` header (a repo, Needs you) are indented 2. The Pinned tab's pins have no header and aren't.
- Line 2, indented under the name, cut with `…`: the question (default fg), the failure (`rate limited`, `overloaded`, `billing limit`, or the reason's first line), the tool and its target (a path keeps its end, `Edit  …/payroll/calc.ts`, and in the short form only its basename), `thinking`, `↳3 subagents · quiet 22s`, `handing back`, or the first line of the last message with markdown stripped. All DIM except the question. Settled agents (exited, no session, and idle with nothing running in the background) have no line 2. An idle agent with background commands has one naming them: `⌁ cargo test --workspace · 4m+` for one (the first printable non-blank line of the command cut with `…`, or its id when nothing in it prints, and how long it has run). The `+` marks the age as a lower bound, "at least, as of the last listing": it counts from the listing that first named the command to the latest, never the wall clock, and an idle agent gets no new listing, so the command may have ended since. It ends every age shown for a command (card, [2] row, [0]'s status). A command line with nothing visible in it (blank, control, formatting, filler or lone combining characters, one rule in `core::visible`) is dropped before it gets here, and so is a task whose id shows nothing, also when it is read back from a saved activity (which then drops only the commands). Core sees the raw text, so the TUI applies the same rule to what is drawn, the text with terminal escapes removed: a command is named by its first line that shows, else its id, and one with neither is left out and not counted, `⌁ 2 commands · cargo test…` for several (the longest running first, no duration). The short form keeps the command's first word: `⌁ cargo · 4m+`, `⌁ 2 · cargo`. Every other card keeps its line 2 and carries commands only as `⌁n` after its name, and the badge is left off when line 2 is the commands line.
- Selection never changes a card's height, and the gutter covers both lines.

### Tier

Which cards get a line 2, worked out from the list at its tallest (every repo open, Needs you's header reserved, and in the Pinned tab every agent that isn't pinned counted as waiting) and the agents with a session, so state changes never change it: line 2 for every agent that isn't settled when that fits [1], else for the first agents `a` would visit while rows remain, else for none. An idle agent's commands line only shows when every card fits a line 2, since it is no one `a` would visit, and otherwise its commands stay the `⌁n` after its name.

### [2] The activity

A list: the activity row `› <first line of the prompt>`, then one row per subagent as `├ ⠹ description  kind  4m` with the last on `└`, then the agent's background commands under a DIM `commands` row that is a heading and no stop for the cursor (commands outlive prompts, so they aren't read as started by this one), one row each as `├ ⌁ cargo test --workspace  4m+`, longest running first and the last on `└`, with the first printable line of the command and how long it has run at least. [2] is one list of lines, the activity, the subagents, the heading and the commands, and what is drawn, which row the cursor is on, what a click lands on and the `n of m` count all read it. They are listed only for an agent with a live session, and the latest listing replaces them. A command that ended while the cursor is on it stays, DIM and as it was and in the place it had among the others, so `n of m` doesn't leap, and [0] keeps its document (headed `no longer listed`), until the cursor leaves it, as a finished subagent does. Its place is where it stood when last listed, so if the others change meanwhile it is only roughly there. A subagent with no description shows its kind DIM in the description column. A subagent that has finished stays until the next prompt, drawn `✓` with how long it ran, so its row and transcript are still there to read and the cursor doesn't jump when it stops. The row under [2]'s cursor also stays after a prompt clears finished ones, until the cursor leaves it. It doesn't count in `↳n`. A running subagent with no tool running and no question open that nothing has been heard from for 5 minutes is lost: it shows the frozen frame and doesn't count in `↳n` until it reports again. An agent waiting only on lost subagents says `↳n subagents lost · quiet 7m` on line 2 (`↳n lost` in the short form), and its activity row `↳0 · n lost`. A stop heard before its subagent's start is held out of sight and finishes the subagent when its start or launch arrives, and a stop for one the activity dropped is never drawn. A finished activity's list of running background subagents replaces the ones tracked, except those already stopped. A file written before the time a subagent was heard was kept counts it from when its agent last reported. The row under the cursor has a Cyan `▌` in the first column while [2] has the keys, and a BOLD description. The title is `[2] Activity`. An agent with no hook reports still has [2], with one DIM row, `no activity recorded`, that the cursor can't be on, and `2` says `no activity recorded · r restarts it through agent`. Its cursor drives [0]: the activity row shows the activity document, a subagent row shows that subagent's transcript and a command row shows the command's document. The harness reads the transcript of the subagent under the cursor off the UI thread (see Main view).

### [3] Changes

Everything git about the agent's worktree, as rows. "Can I merge this" and "is anyone else in this file" are questions about the work, so they're answered here and in [0]'s diff title.

- Title: `[3]` then two tabs as [1]'s title has them, `Uncommitted` and a second tab named for where the checkout is, `Branch` or `Unpushed`, the active one BOLD and the others plain with a DIM ` · ` between. Both show while they fit the width and only the active one below that, so the form never follows the cursor. Then the active tab's totals (`+` Green, `−` Red), then `∩ n` (Yellow) when n files are shared with other agents in the repo. `[` and `]` cycle the tabs while [3] has the keys (the footer's `]` hint and the help name the actual next tab), and the choice is kept for the session. The default is `Uncommitted`. Tabs are a per-panel concept in the keymap: `[` `]` is bound once for [1] and once for [3], each with its own label.
- **Uncommitted** lists only files with uncommitted state (staged, unstaged, untracked or deleted), counted against the last commit (`git diff --numstat HEAD` joined with `git status`, both with `--no-optional-locks`), untracked files by their own line count in both tabs (all added, read from the file, binary when it has a NUL in its first 8000 bytes). A file row says `new` before its count (`new +9`), and `new` alone when the file is empty or wasn't read. Reading stops at 8 MiB per facts read, and a file that doesn't fit what is left, or isn't a plain file, isn't read. The numbers mean what isn't committed. **Branch**: what this branch changes compared with where it left `origin/main`, like a PR plus your uncommitted work. **Unpushed**: on the trunk (the local branch the default branch is a remote copy of, `main` on `origin/main`), commits not yet on origin plus uncommitted work. A push empties it. Both are the diff from `merge-base(HEAD, origin/HEAD)` to the working tree: committed and uncommitted work together, where uncommitted files keep their markers and files that are only committed have none. Hovering a file reads its diff against the same base as the tab it's in (`DiffBase::Head` or `Fork`).
- First row, on the second tab only: the branch summary, short enough for the narrow sidebar, `↑27 · 4 uncommitted`, each part left out when it's zero, `↓n` when the default branch has moved on, and `nothing to push` (trunk) or `no changes` when all are zero. Uncommitted has no such row: it lists only its files, and hovering one of them never shows the branch. What is compared with what is left to [0]. A detached HEAD is named by its short sha. With no default branch to compare with the tab is `Branch` and only uncommitted files are listed. Which of these applies is `Compared`, read with the worktree's facts. A main checkout shows the row only with uncommitted files, and an agent worktree shows the nothing form only once it's done. It is a row the cursor can be on, and then [0] shows the branch: titled `Unpushed · main vs origin/main` or `Branch · fix-thing vs origin/main` (`<sha> vs …` detached, `· no base` without one), then `Commits (n)` and `Uncommitted (n)`, and `behind origin/main by n` when behind, so committed work stays reachable. When a tab has nothing to list, [3] stays and its one DIM row, which the cursor can't be on, says why: `no changes` (git was read and the tab lists nothing), `reading git…` while the facts are asked for and haven't come back, `no checkout` for a session with no worktree, or `git: <why>` (its first line) if git couldn't be read. The title keeps the tabs, and the corner counts files only once git was read. The row is about the worktree rather than a file, so it is DIM behind the files' gutter column. The panel's bottom-right corner counts the active tab's files (`4 files`).
- Two views, switched with `` ` `` (lazygit's key) and remembered for the session. The default is the **tree**: folders before files (each group alphabetical), a chain of single-child folders on one row (`crates/tui/src`), `▼` open and `▶` closed before a folder's name, two columns of indent per level, and a file under its folder with its name only. A folder row carries its files' summed counts in DIM (`+16 −3`, or `new` / `bin` when nothing has line counts). `⏎` on a folder opens or closes it, `-` closes every folder and `=` opens them all. What's closed is kept per agent by every real folder path, so a chain row (`a/b/c`) is closed when any folder it stands for is: `⏎` closes it at its deepest folder and opening it opens all of them, `-` closes every folder including the intermediate ones, and a chain that splits or merges as files come and go keeps its folders' state. A folder that appears starts open, and closed folders that no longer exist are forgotten when the agent's facts are read again. The cursor is held by identity (the file's or folder's path, or the readiness row) and re-resolved after each read, falling back to the nearest row, so a refresh above it never moves it to another file. The built rows are cached per agent until its facts, the view or its closed folders change. The cursor stays on the folder it toggled, and on the folder holding it after `-`. `` ` `` keeps it on the same file, and switching tabs keeps it on the same path when the other tab lists it (or a folder holding it) and otherwise puts it on the first row (the branch row on the second tab, the first file on Uncommitted). The **flat** list is the files in numstat order as below. The branch row, when the tab has it, stays first. In [0] a folder under the cursor lists the files under it with their counts (read from the git facts already loaded, so nothing waits on git, rather than one combined diff per folder), titled `<folder>/ n files +a −r`. `e` on a folder opens `$EDITOR` in that folder.
- Flat: a row per file in numstat order, counts right-aligned in columns. A file another agent changed too carries a Yellow `∩` before its counts, and the column is kept so the counts stay aligned. Paths keep their last 3 components (`core/src/activity.rs`), fewer while they don't fit.
- Every row opens with a three-column marker, in both views, so committed and uncommitted files read apart. A file shows lazygit's `XY` code: the index letter (`M` modified, `A` added, `D` deleted) in Green, then the working-tree letter in Red, `??` in Red for an untracked file, and nothing for one that is committed and clean now (only the second tab lists those). A folder shows a Green `●` in the first column when a file under it has staged changes and a Red `●` in the second when one has unstaged or untracked changes, and nothing when everything under it is committed. On the second tab a file that is dirty but identical to the fork point (staged, then reverted) isn't listed, since that list is the diff from the fork. The marker keeps its width and the path is what truncates.
- A Cyan `▌` marks the row under the cursor while [3] has the keys. Who else changed the file is in [0]'s diff title, where every name fits.

**Open elsewhere.** Zellij sizes a session to its smallest client, so a second window squishes the other. A client is another window when it isn't this TUI's own pty child and has no `agent` TUI above it in its process tree, found by argv: `zellij attach` or `a` with flags anywhere, and `zellij -s <name>`. An `agent` with no subcommand or `tui` is a TUI, so a second TUI's preview never counts and both show the terminal. `agent attach` and the other subcommands are part of a window and the walk goes on past them. One look scans the process table once for every session at the same time (`ClientControl::windows`), on a worker thread of its own for each kind of look (see below), newest ask first, and each answer carries a ticket so an older one is dropped. A look is asked before a preview or an attach to an agent the TUI isn't already connected to, and at every refresh unless the pane is itself waiting on a look or a client. Its answer is kept per agent in that agent's record (`Tracked::company`), the one place the pane, the cards and the banner read, so they can't disagree. An agent a look doesn't list is alone again, and an agent that leaves the snapshot takes its record with it. A look is a `Refresh` (the periodic one, which keeps the cards and the pane current) or a `Decision` (before attaching, and after a close). Each kind has its thread, so a refresh scan still running can't make the two-second wait late. Moving here notes the session alone once the new client exists and drops every look asked before that, so a slow answer can't show the closed window again. A paused pane never outlives its agent: it is emptied when the agent leaves the snapshot, and a failed look on one whose windows are gone attaches again. A pane still waiting after two seconds attaches without the answer, quietly, since slow isn't broken. A look that fails attaches too and says so once in the status bar. While a session has another window the TUI holds no client: [0] is paused and shows the agent's activity under the banner, every card of an agent with another window carries a DIM `⇄`, not only the selected one, and when the check finds no other window the preview attaches again. Only `⏎` or `i` in [1] on that row, while its banner shows, moves here: it attaches first and closes the other windows only once connected (so a failed attach closes nothing). Every other way to reach it (`0`, the nav key twice, `a`, the switcher, `i` from another panel, `⏎` in a peek of it) lands in NAV with [0] paused and says the agent is open elsewhere. If a window opens while the keys are in AGENT it is left alone and the corner and card turn Yellow, and the nav key then drops the TUI's client so the other window gets the full size. `s` still sends, since writing to the pane needs no client. `v` on a paused agent peeks through a read-only observer instead of a client, so the other window keeps its full size (see Observer under Peek). 

**Places.** Each window is named from its client process's ancestors, nearest first, in the zellij adapter, so the core only sees a closed `Place`: `Nvim`, `Ssh`, `Tmux`, `Terminal(app)`, `Detached` and `Unknown`. The first ancestor that names a place wins and shells, `agent` and `zellij` name none. An ancestor is known by the basename of its argv[0] (cut at a `:`, as `sshd: user@pts/0` is), and by the kernel's name only when that says nothing, since Linux cuts it to 15 characters. `nvim` or `vim` is `Nvim`, `sshd` (or `mosh-server`) is `Ssh`, a `tmux` anywhere up the chain (its server runs with ppid 1) is `Tmux`, and a known terminal (`wezterm-gui` and `wezterm-mux-server` as `wezterm`, `ghostty`, `iTerm2` or a program starting `iTermServer` as `iTerm`, `Terminal`, `alacritty`, `kitty` and a few more) is `Terminal` with its short name. A chain with none of these is `Detached` when it has no shell above the client either (the window that held it went away and left it under init, which is what an orphaned client looks like), and `Unknown` when it has one. A split beside the TUI and another tab are the same place, so nothing says `another tab`. The copy is the same in the banner, the status message, the corner and the peek title: `in nvim`, `over SSH`, `in tmux`, `in wezterm`, `detached window` for `Detached`, `elsewhere` for `Unknown`, and `in 3 windows` when several windows show the agent and they are not all in one place (two nvim windows say `in nvim`). The banner adds `· ⏎ move here`.

- **Status.** Whenever [0] isn't the terminal, the top-right of its border carries the selected card's state: glyph, name, what it's doing and for how long. The glyph, name and time are reserved first, so the title yields to them (a path keeps its end, who else changed the file shrinks to `∩ auth-refresh-2 +1`), and what it's doing shows only with at least 14 columns. A delegating gist already ends in the quiet time, so no second time follows it. An idle agent with background commands says them there as its card's line 2 does. An agent that asks opens a Yellow banner row at the top of [0] with the question and `i answer`, except on the activity view, which pins the whole question under its own status row. It never switches [0] to the terminal by itself, since taking a diff away from under the reader is worse than one keypress.
- **In the pane** means its terminal is visible in [0], not that it's selected. Done doesn't clear while its diff or activity is on screen, and `a`, the bell and the status counts treat it as not in the pane.
- **The pty keeps its size.** Its rect is the terminal area for the screen mode and window, whatever [0] shows. Only `+` and `_` resize it. The reader keeps feeding the parser while the terminal is hidden.
- **Folders.** The file list shows at once from the git facts. The diffs are one document per folder and facts epoch (which read of the git facts it came from), read off the UI thread through the same loader and cache, against what the active tab does (HEAD on Uncommitted, the fork point on Branch and Unpushed). Diffs of those files already in the cache are reused, each file keeps the per-file line and byte caps, and the folder stops after 20 files or 5000 lines in all, ending `+k more files, open one to see its diff`.
- **Diff cursor.** With [0] focused on a file's or a folder's diff, `j`/`k` move a Cyan `▌` over its lines (hunk headers are skipped), `g`/`G` go to the first and last, `[`/`]` jump to the previous and next hunk, and `e` opens the file in `$EDITOR` at the line (`+N` before the path, as tig does), a removed line at the line that now follows it. Every diff row has a one-column gutter for the cursor. The line positions come from each `@@ -a,b +c,d @@` header.
- **Files and ranges.** `J`/`K` with [0] on a diff jump to the next and previous file: in a file's diff they move [3]'s cursor to the neighbouring file (over folders and the branch row) and [0] keeps the keys, in a folder or commit they jump to that file's section. `V` starts a selection at the cursor, `j`/`k` extend it, and `c` comments on all the selected lines as one comment (labelled `path:10-14`). `Esc` drops a selection before it leaves [0].
- **Copy.** `y` with [0] focused copies through the terminal's clipboard (OSC 52, which wezterm supports), at most 70000 bytes: in a diff `path:line`, or with a `V` selection the selected lines without their `+`/`-`, on the branch a commit's sha or an uncommitted file's path, in a log, a subagent's or the activity's, the entry under the cursor (the prompt or text, or a call's input and result), and in an activity document with no log the agent's message. The status bar says what was copied. The subagent's report isn't an entry and isn't copyable yet.
- **Branch cursor.** With [0] focused on the branch, `j`/`k` move a Cyan `▌` over its commits and uncommitted files, and `⏎` opens the one under it: a commit shows the files it changed and each file's diff against its parent (read off the UI thread like a folder's, with the same 20 file and 5000 line caps, titled `[0] commit abc1234 subject`), an uncommitted file shows its diff against the last commit. The commit view takes the diff cursor, `e`, `c` and the other diff keys. `Esc` goes back to the branch with [0] still focused, and a second `Esc` leaves [0]. `e` on an uncommitted file opens it in `$EDITOR`.
- **Review comments.** `c` on a diff line opens a one-line box, titled `Comment · path:line · for agent` with the quoted lines DIM above the input. `⏎` adds the comment to that agent's draft (kept in memory across selection changes), empty text on a commented line deletes it, and `c` on one edits it. A commented line shows `✎` in the gutter and the status bar counts `n comments`. `s` with a draft reads `send review`: the typed text is the overview, and `⏎` builds one message in the nvim review tool's shape (`path:line`, the quoted lines as `> ` lines, then the note) and hands it to the ordinary send path, so every refusal applies. The draft clears once the message goes to the worker and comes back if it isn't typed. `q` confirms while drafts exist. `c` checks out a branch only from [1], [2] and [3]. Nothing in [0] writes to git.
- **Loading.** Diffs and branch logs are read off the UI thread once the cursor has rested 60 ms on a row, keyed by what makes them change (a file's numstat line or a branch's counts, and how many times the agent's git facts were read, so an edit that kept the counts still shows). The last 32 are kept, within 8 MB, and a read that failed is shown for 5 s and then asked again. A file read again keeps its old text on screen meanwhile. Another file never shows under this title, only blank, with a DIM `loading` in the corner after 150 ms, so holding `j` never flickers. Git's output is read up to 2 MB and each line is kept to 2000 characters, so a huge diff is never held whole. Hunk headers are cut with `…` and code wraps. A diff over 5000 lines shows the first 5000 and ends with `12,340 more lines · e open`. A binary file reads `binary · 48 KB`.
- **Transcripts.** The harness reads the tail of the subagent's transcript when the cursor lands, soon after its agent reports, and every 10 s while it runs, and stops once the transcript says it finished. [0] shows a pinned status row and a DIM rule, then the scroll region. The status row says whether it progresses: `⠹ working 4m12s · 37 calls · 1 error · sonnet`, `⠋ working 14m · quiet 6m ? · …` after 5 minutes with no record and no running tool (the spinner stands still), `! failing · cargo build failed 4 times · …` when one call failed three times since it last succeeded or three of the last five calls failed, `! stopped · API error …` when the transcript ends in an API error record (matched on `isApiErrorMessage`, not yet seen in the wild), `✓ finished in 6m02s · 52 calls`, or `● ended after 6m02s · no report`. Counts read `400+ calls` when the tail didn't reach the transcript's start. The prompt is one row and `+n lines`. Each said block starts a phase after a blank row, and its calls sit indented under it. A call is one row, `● Tool  target ··· summary  12s`: the target is the command without a leading `cd … &&`, a path relative to the checkout, a `"pattern" in path`, and so on, and the summary is read from the structured result (`730 lines`, `+9 −14`, `11 matches`, `new · 120 lines`, `exit 101`). Both sides are cut so nothing overflows the row. A failed call (`is_error` or `Exit code N`) is `!` Red with up to three `⎿` rows of stderr under it and `+n lines`. A succeeded Bash call whose output holds a failure line (`test result: FAILED`, ` FAILED`, `panicked at`, `error:`, `FAIL`, a nonzero `n failed`) is `●` Yellow with those lines under it. Three or more successful Read, Grep, Glob or LS calls in a row fold into `● Read  4 files  a · b · c +1 ··· 3.4k lines`, and the same call twice or more in a row into one row with `×n` whose outcome is the latest. A running call shows a spinner and `running 12s`, with a Yellow `?` after 5 minutes. Call durations show from 5 s. Below 100 columns the summary column shrinks to 10 and a finished call's duration replaces its summary. A finished subagent shows its `Report` (its handback message, else its last message) between the prompt and a DIM `Calls · n` rule, and opens at the top, with a subagent finishing while followed jumping there. A running one opens at the tail and follows, scrolling up pauses it, and `G` resumes. With [0] focused, `j`/`k` move a Cyan `▌` cursor over entries (the prompt, a said block, a call, a fold), `⏎` expands the entry (the whole prompt or text, a call's input and result up to 40 lines, a fold into its calls), `=` and `-` expand and collapse all, `g`/`G` go to the first and last entry, and `⌃D`/`⌃U`/`PgDn`/`PgUp` page with the cursor. Expansion is kept per subagent until its row leaves [2]. `e` writes the transcript as Markdown (the raw `.jsonl` path, the report, then the prompt, what it said and each call's input and result under `Calls`) to `agent-transcripts` in the temp dir and opens it in `$EDITOR` at the cursor's entry. A subagent with no transcript file reads `no transcript for this subagent`. The prompt and the report are kept whole, up to 8000 characters, and a call's input and result up to 1000 and 2000.
- **Activity.** The harness reads the agent's current activity off the UI thread (`Harness::activity_detail`, through the same worker queue as subagent logs) while [2]'s cursor is on the activity row: when it is first shown, soon after its agent reports (at most every 2 s) and every 10 s while it works. Every hook payload carries the agent's `transcript_path`, which `agent event` records in the agent's activity as an opaque `TranscriptRef` (a subagent's payload never sets it). The path is used only when it is a `.jsonl` file under the harness's projects directory (compared canonicalised), and otherwise the worktree's newest conversation is read, the one launch would resume. A transcript its conversation has moved on from (a session moved to the background is forked, and the original ends in `continued-in` records naming the fork) is replaced by the newest transcript of that chain that holds messages, for the activity and for the interrupt probe alike. The read takes the last megabyte of the transcript, widening fourfold to 8 MB while it holds no prompt, and cuts it at the last real prompt: the last user record that isn't meta (`isMeta`), a compaction summary, a local command (`<command-name>`, `<local-command-…>`), an interrupt marker, a background agent's notification, or a tool result, and has text. A slash command counts only once work follows it (the meta message holding its expansion, or the agent's own reply), so `/model` and `/clear` leave the activity alone and `/simplify` starts one titled `/simplify args`. Every user record of an activity shares a `promptId`, which names the activity (`ActivityMark`) when the prompt itself is out of reach, and a new mark starts the entry cursor over. `system`/`turn_duration` ends the activity and gives its length, unless the agent worked after it. A harness that sends no event when the user stops a turn says so on every report (`InterruptSignal::Transcript`), and for it the TUI reads the transcript. Claude Code writes a user record naming the `interruptedMessageId` it stopped, or holding one text block `[Request interrupted by user…]`, and no hook fires. Every such agent that is working or delegating is read, not only the one shown, and so is one that is interrupted, since it may carry on. `Harness::interruption` runs off the UI thread at most every 2 s per agent, stats the file and reads nothing while its length and modification time match the last read's, and otherwise reads the last 64 KB, widening fourfold to 1 MB while it holds no conversational record. A last line without its newline is still being written, so nothing is concluded from that read and no stamp is kept. Bookkeeping records (`last-prompt`, `cost-state`, snapshots) between conversational ones are ignored. Only records later than the proof's `after` count (when the activity began working, or when it was interrupted), so a marker from an earlier turn is `Older`. The answer is `Interrupted` with the marker's time (the newest record is the marker, and the agent counts as interrupted from that time, so work landing within the detection lag still reads as going), `Going` (it is work), `Older`, `Unchanged` (nothing to conclude, no stamp kept) or `NoTranscript` (that proof isn't read again). The store applies `Interrupted` to a working agent (`Activity::interrupted`) and `Going` to an interrupted one (`Activity::resumed`), each only while the activity is still at the report count of its proof (`Going` or `Stopped`, which only `Activity::going` and `Activity::stopped` make), so a read that a newer prompt or report overtook changes nothing. The worker then sends every agent's activity at once, so it shows without waiting for the poll, and a read that fails is told once. The agent becomes `Interrupted` (a card with `■` and `interrupted`, the status row `■ interrupted · 1m · 10 calls`, a running call no longer spinning). Open questions and foreground subagents are dropped (background subagents stay). It stays until the next prompt, a tool start, or the transcript showing it went on, and it isn't in Needs you, the bell or the counts. A `queued_command` attachment (its prompt a string or parts, of which the text is kept) is a message the user sent mid-activity (`› queued: …`) and `compact_boundary` a DIM `compacted` row. An activity over 8 MB starts truncated (`400+ calls`). It is the log idiom above with these differences. Every call carries what it does (`CallKind`: explore, edit, delegate, ask), so the views never name a harness's tools. The pinned status row follows the hooks, not the transcript, and its elapsed time counts from when the agent last went to work, so a hand-back that wakes it after the activity ended starts again at 0: `⠹ working 6m12s · 23 calls · 1 error · 2 files · ↳1 · ⌁1`, `! failing · …` by the same rule, `⠋ delegating · ↳2 · ⌁1 · quiet 40s`, `✓ finished in 8m40s · 31 calls · 2 errors, all recovered · 3 files · 2 subagents · ⌁2` (`●` and no colour once seen), and `! failed · rate limit · 3m`. `⌁n` counts the background commands wherever `↳n` or the subagent count shows, and like them it is left off the narrow working and finished rows. While it asks, `◆ asking 2m · header` and the whole question stay pinned under it. What it asks about is resolved from the ask's tool id against the activity (`Asking`: a question call with its questions, a permission prompt for one call, or a subagent's question, drawn as `↳ name asks`), and an ask the transcript hasn't caught up with shows the hooks' text: every question's text and its options as numbered rows, each description beside its label or under it below 100 columns, then `Other`, capped at three quarters of the panel. A permission prompt pins the sentence the agent said before it and the whole call, at most 6 rows, and the waiting call row reads `◆ … waiting 2m`. Every phase but the latest folds to one `▸ <first line it said>` row with `n calls` and what stands out (errors, else `+a −r`, else `↳n`, else a duration over a minute). A phase stays open while it holds a running call or a failure no later call has succeeded after, and `⏎` opens one, `=`/`-` open and close all. A finished activity folds them all under its closing message, shown in full with Markdown emphasis (`**`) stripped (the Stop hook's message, else the transcript's last line) before a DIM `Calls · n` rule, and opens at the top like a finished subagent. A working or asking one follows the tail. `── since you looked · 2m ──` goes before the first entry newer than the last moment the activity view, or the agent's terminal, had been in front of you for 3 s, and goes once you've looked again. The same dwell time acknowledges a finished activity, so the `✓` and the marker clear together. A harness with no transcript, or an agent with no activity yet, shows the hooks' account (the prompt, the message, the subagents, then the background commands under the same DIM `commands` heading [2] uses) or a DIM `no activity yet · s send` in the middle. What its entries link to, and the files it touched, are under Touched files and links. Not built yet: the answer keys.
- **Command output.** The harness reads the end of a background command's output off the UI thread (`Harness::command_output`, through its own worker queue keyed by agent and command) while the command's row is what [0] shows: when it is first shown, and 3 s after the last answer while it stays shown. Switching to another row and back asks again only when the last answer is older than that, and the last answer stays on screen while the next read is in flight, so a listed command never goes back to `reading…`. A request the worker has held for 15 s is made again, and the answer to any request of the wait counts, so reads that always take longer still end in an answer. Until the first answer comes the section reads `reading is taking long` instead of `reading…`. An answer to a request from before the wait began, or for a command that is no longer tracked, is dropped. The `Output` section sits below the facts, all DIM: the heading, `showing the last 64 KB` when the file was longer than what was read, the text, then `last output 4m ago`, how long ago the output file last changed (its modified time, so it doesn't move when the output is read again, and it is left out when the file has no time). The facts above it keep the listing's own `as of`. It follows the end like a log, scrolling up pauses it and `G` resumes (the corner says `following` or `paused …`). A paused document keeps its place in the text when the 64 KB window drops old lines at its front or a row above the text (the cut note, a failure) appears or goes: the dropped lines are counted exactly from where the window's start moved in the file when the new text carries on from the old, and from the lines themselves otherwise, which is ambiguous only for runs of identical lines. The count can be one row off where a run of blank lines straddles the cut, and drifts when invalid UTF-8 was replaced. A scroll above the `Output` heading never moves, one on a row between the heading and the text moves with those rows but not with dropped ones, and when nothing of the old text is left a paused view goes to the start of the text. With nothing to show the section says `reading…`, `no output yet` (the file has no bytes), `output file gone`, `looking for the output…` (the search of the transcripts is bigger than one request reads, and goes on the next time), `no output location recorded` (neither the agent's transcript nor its subagents' says where the command writes) or the cause of a failed read. A failed read keeps the last output it found on screen with `couldn't read it · cause` above it, and the status bar says it once until a read succeeds again. The text is the command's own, so only printable characters of it reach the screen: escape sequences are stripped first, a carriage return rewinds its line so only the last visible text after it shows (`50%\r100%` reads `100%`, and `done\r<erase line>` keeps `done`), a backspace deletes the character before it, the characters that print nothing and can disguise text are dropped (bidirectional controls, zero-width spaces and direction marks, the word joiner, the byte order mark, tag characters, the soft hyphen, the Hangul fillers, the Mongolian vowel separator), while the zero-width joiner and non-joiner, marks on a letter and blanks that are part of real text (the braille blank, Khmer inherent vowels, Mongolian free variation selectors) stay, though `core::visible` counts all of those as leaving no mark, a tab is one space, binary and non-UTF-8 bytes are replaced, runs of blank lines are one, only the last 5000 lines are kept and long lines wrap. The rows are wrapped when the model settles, for [0]'s width and each new answer, so a draw only reads them. Claude Code writes the output to a file named in the transcript's record of the call that started the command: a user tool result whose text starts with `Command running in background with ID: …` (or the timeout form, `… moved to the background (ID: …)`) and says `Output is being written to: …`, with a `backgroundTaskId`, when it has one, naming the same task (a record with one may have the command's own output before the announcement). The path is the word after `Output is being written to: ` (quotes and a closing `.`, `,`, `;` or `)` are dropped), which must end in `/<task id>.output`. A path with spaces in it is not found that way. Before any transcript is searched the harness looks for `tasks/<task id>.output` as a regular file (a link is skipped) in each session directory of the agent's project under the task root (`<tmp>/claude-<uid>/<project>/`, the project being named from the agent's resolved path), and remembers what it found, reopening it through the same checks on every read and listing the project again every tenth read so that a newer file of the same name replaces it. A remembered file that is refused (swapped for a link, another owner, unreadable) is forgotten and the transcripts are used instead, and the refusal is only reported when they name nothing either, since a task id is unique and Claude Code names a task's directory after the session its process started under, which a `/clear` or a resume leaves behind and no `continued-in` record links. How Claude Code names the project for a path reached through a link, or one too long to be a directory name, is unverified here (the project directory is named from the resolved path, which is what every transcript directory seen so far matches), and a project that can't be listed or named leaves the search to the transcripts. Otherwise it searches the transcript and the transcripts of the agent's subagents beside it (`<session>/subagents/agent-*.jsonl`) once and then only what was appended, reading at most 32 MB of unsearched text per request, and a path it found is kept with its session. The path is opened once and the opened handle is what is read: absolute, resolved through any links to `<tmp>/claude-<uid>/<project>/<session>/tasks/<task id>.output` where `<uid>` is the running user, whose directory and file that are, opened without following a link or waiting on a pipe and a regular file. Anything else is a failed read, and only the last 64 KB is read, by seeking. A command its agent no longer lists is read once more if the read whose answer came last was asked while it was listed (also when a stalled request was asked again after it ended), and again while the harness is still looking for where it writes, then keeps what it had and is marked `no longer listed`.
- **Peek.** `v` opens a floating window centred over everything, showing the selected live agent's terminal at exactly the pty's current size (a pty bigger than the screen is cropped from the top so Claude's prompt at the bottom stays visible, with `cropped, showing the bottom` on the bottom border, and it is never resized for the float). What's behind it is dimmed. The double Cyan border carries `<glyph> <agent>  <state> <time>` on the left and `⏎ enter · s send · Esc close` on the right, and the footer says the same, under a `PEEK` badge. No key reaches the pty while it is open: `s` opens the send box for that agent (the peek stays behind it), `i` or `⏎` enters AGENT with the normal border, and `Esc` or `v` closes it. `t` says `send is s now`. The terminal counts as visible while peeking (the done-clear and `a` see it), and the mouse is ignored.
- **Observer.** A session another window shows is peeked through a read-only watcher, `zellij watch <name>` in a pty (`SessionHost::observe`), not a client. In zellij 0.45.1 it isn't counted in `zellij action list-clients` or the session's `connected_clients`, doesn't resize the session, ignores every key it is sent (`q`, `Esc`, `⏎` and `⌃C` did nothing), and exits when the session ends as long as its pty is read (an unread one blocks forever, so the TUI reads it every frame like any pane). It draws the whole session at the session's own size from the top-left corner and crops to a smaller terminal, so the watcher's pty is sized to the session's `display_area_columns` by `display_area_rows` (the active tab's, else the first's, from `zellij action list-tabs --json`, read by a worker job before the pty is spawned), at most 500x200, and the peek's crop shows the bottom. The process scan never counts `zellij watch` as a window. A client's keys can't reach a watcher, its pty is never resized to [0], and closing the float drops it. `⏎` and `i` enter AGENT only on a client: in a watched float they close it and leave the agent paused, and attach instead when the other window has gone. Each look reads the watched session's own company. When it finds the other window gone, the float goes back to showing the pane and a client attaches under it, and when it finds a window beside a client the float is over, the client is dropped and the float watches. Each look while watching also asks for the size again, and when the other window was resized a new watcher starts while the old one keeps showing. When the size can't be read the float closes and the status bar says `couldn't peek at X: why`. While the size is awaited the float says `watching X…`. When the watcher ends (the session ended, `zellij watch` failed), the pane's connection ends under a float, or the snapshot says the watched session is no longer live, the float closes and the status bar says `peek at X ended`, followed by `: ` and the last line the watcher printed (or its non-zero exit status) when there is one.
- **Mouse.** A click on a row of [2] or [3], the readiness row included, focuses that panel with its cursor on the row, so [0] shows it. A click inside a document focuses it. A click on the terminal in [0] doesn't enter AGENT. The wheel scrolls the document under it, and over [2] or [3] it moves that cursor. Hit rows are recorded as drawn, so they stay right after a panel scrolls.

- **Touched files and links.** Once the activity has settled (done or failed) a `Touched files` block follows the closing message, a row per file in [3]'s marker and current counts. While it works, asks or delegates, the status row only counts them. The files are the targets of edit calls that didn't fail (`Call::touched`) joined with the files whose entry in the agent's git facts differs from the one noted when a prompt began an activity. That snapshot is taken when the agent's prompt count moves (`Activity::has_new_prompt_since`), so a subagent's hand-back or a session starting again doesn't reset it. It is only taken from facts that were asked for (the event count travels with the request and comes back with the answer) after the agent's last report before the prompt and no later than the prompt's own event, so they hold neither the previous activity's last edits nor this one's. Otherwise there is no snapshot and only the edit calls speak. A touched file git hasn't been read for shows no counts, and one git reads as unchanged says `no difference`. Paths the harness names are made relative to the checkout (also through a symlink, with the checkout resolved when its facts were read, and with `.` and `..` folded), so one file is one row. An untracked file already present when the activity began counts as touched once its lines change, since its entry in the facts then differs from the snapshot's. ## Repos

The sidebar shows a repo while a session or an agent worktree belongs to it, and while it's **listed**: kept in `~/.local/state/agent/repos` by `agent add`, the picker, `agent repo`, or creating an agent in it. A listed repo with nothing running is one row, its main checkout, so `⏎` starts the repo session there. A repo whose directory name can't be a session name can't be listed. `agent forget` drops the listing. A listed path that isn't a repo any more is a discovery warning, not an error. The **catalogue** is what the picker and the `n` form offer beyond that: `[repos] dirs` in the config, each a repo or a directory of repos, read without running git (a `.git` directory is enough, and linked worktrees are left out). Paths are canonical so a found repo matches its listing. It's rescanned with every refresh, never puts a repo in the sidebar by itself, and what couldn't be read there is reported like a discovery warning.

## Views

Three tabs in [1], in the order Agents, repo, Pinned, with Agents the one the TUI opens on (the saved selection is restored within it, and the tab itself isn't saved), cycled with `[` and `]`, named in its title where the width allows (see Layout) and otherwise only by the footer's `]` hint, which names the next tab (`agents`, `repo`, `pinned`). Moving between tabs keeps the selected agent when the new tab lists it. Otherwise the tab selects its first row (in Pinned the first pin, else the first Needs you row) and remembers what was selected, so the next tab that lists it, or a full cycle, comes back to it unless you moved in between.

- **Repo (Focus, default)**: one repo, named by the selected row's repo in the title, no per-repo header rows. The main checkout is labelled by its branch, never `(root)`.
- **Agents (Overview)**: an accordion. Repo rows are selectable items with `▸`/`▾` (DIM) and collapsed repo rows show right-aligned nonzero counts of settled agents in `● ○` order (waiting agents are counted under Needs you, and open repos show none), each glyph a space before its number and pairs two spaces apart (`● 1  ○ 2`) (idle `·` worktrees are not counted). Every repo is open when the whole list fits with one-line cards. Otherwise the repos furthest from the selection close first, and the repo holding the selection always stays open. Like the tier, this counts every place an agent could be listed, so agents changing state never open or close a repo. A repo whose agents are all under Needs you has no row. Cards are indented under the repo, and line 2 sits under the name. An agent under Needs you isn't listed again under its repo, and the selection follows an agent as it moves between them, keeping its screen row when the list scrolls. A repo whose only entry is its main checkout collapses to one row.

## Keymap

AGENT: `nav` → NAV (cursor on current agent). `nav nav` (within two seconds) → NAV with the previous agent selected and previewed. `prev_agent` and `next_agent` (default `⌥,` and `⌥.`) → the neighbouring agent, with the keys still in AGENT (see Always-on chords). Everything else goes to the pty. In NAV, `nav` does nothing unless it directly followed the nav key that left AGENT.

### Always-on chords (owner)

The keymaps are unavailable while an agent has the keys, so moving between agents sent the owner to the mouse. `prev_agent` (default `alt-,`) and `next_agent` (default `alt-.`) work in both modes and ship on, with an opt-out. They are the only keys besides `nav` and its escape hatch that AGENT takes from the agent.

- **Order**: [1]'s visible list, top to bottom as drawn (repo rows are skipped, Needs you comes first, a filter or tab narrows it), wrapping at the ends. With fewer than two agents it does nothing and says nothing. It steps to the adjacent row, so it doesn't jump over an exited agent.
- **NAV**: moves the selection to the neighbour and previews it through the same `select` as `a` and the switcher, so it stays in NAV, from any panel. A neighbour that is the TUI's own session, still starting or restarting says so as `select` does.
- **AGENT**: the chord is not sent to the agent. The keys go to the neighbour and stay in AGENT there: the user is already typing into an agent and pressed a deliberate chord, which is the explicit request. It is carried like `⏎` (`Landing::Hop`, which enters like `Landing::Enter` with the seat, through the check for other windows). It walks from the agent being typed into to the first agent that can take the keys, skipping the ones that can't (not running, starting, restarting, this TUI's own session, or shown in another window), so one stuck neighbour never blocks the chord, and says `no other agent to hop to` when there are others and none can. A neighbour that another window turns out to show only once the check is back leaves the keys in NAV on it, paused, as `⏎` would. A second chord before the first has connected goes on from the pending agent.
- **Typing during a hop**: the old agent is let go at once and the new one takes a moment: the check for other windows (a few ms, up to 2 s), the client, and its terminal's first output. Until that output has been read every key and paste is held, never run as a NAV key, so `dry` typed after the chord can't kill anything. It is then written to the new agent's terminal encoded with the modes that terminal has set by then (bracketed paste, application cursor keys), so a held paste arrives as one paste. If the terminal prints nothing within 3 s what was held is dropped. At most 4 KiB is held. Past that nothing more is kept and nothing at all is delivered, since the keys after a missing paste would type something nobody wrote. The nav key or the escape hatch gives the hop up, drops what was held and, before the client exists, previews the target in NAV. A hop that doesn't land (the cursor moved, the agent went, another window shows it) drops it too. Every drop is said, as `dropped 3 keys and a paste`, and joined to the message that follows it, as `x: ⇄ in nvim · ⏎ move here · dropped 2 keys`. The first output chunk ends the wait even when it is partial, so modes that arrive in a later chunk than the first burst are missed. The mouse isn't held and isn't forwarded while the wait lasts. If the pty's writer has failed, the next write says `couldn't type into <agent>: its terminal no longer takes input, input lost`. The write that actually failed is lost without a word, since the writer thread only finds out afterwards.
- **Overlays and the peek** keep their own keys, so the chords do nothing there.
- **Esc then `.`**: a legacy terminal sends Alt+`.` as Esc followed by `.`, so Esc and `.` typed quickly (leaving insert mode and repeating in Claude Code's vim mode) look like the chord and can't be told apart. `next_agent = "none"` is the opt-out.
- **Config**: `[keys] prev_agent = "alt-,"`, `next_agent = "alt-."`, any key spec `nav` takes. `none` or `off` turns that one off, and then the key goes to the agent as any other. `alt-.` is readline's yank-last-arg, which the chord takes from a shell agent, so `next_agent = "none"` is the opt-out for one that needs it. Duplicates (including with `nav`) are refused. A chord the terminal can't send falls back to its own default, as `nav` does, or is left off when another key has that default. A default another key you set has (`nav = "alt-,"` against the default `prev_agent`) is left off and listed under Keys in `?` (`prev_agent default ⌥, is taken by nav, off`), never an error, but two keys you set to one key are refused.
- **Option on macOS**: terminals that don't send Option as Alt by default deliver nothing for the chords until it is enabled: Terminal.app (Profiles > Keyboard > Use Option as Meta key), iTerm2 (Profiles > Keys > Left Option key: Esc+), Ghostty (`macos-option-as-alt = true`), Alacritty (`option_as_alt = "Both"`), WezTerm (the left Alt sends Alt by default, unverified). The setting names come from the terminals' documentation and haven't been tried here.
- **Why not Ctrl**: a Ctrl chord is a control byte that readline, vim and the agent's own TUI already use. `alt-` keys arrive as `Esc` plus the character on every terminal and as a modified key under the kitty protocol, both matched exactly (`alt-,` doesn't match `alt-<`).

NAV. The table in `crates/tui/src/keymap.rs` is the source of truth for the footer and the help, and a test checks that every key the handlers match is in it. Keys that do nothing in the focused context aren't offered.

Confirms only when it would interrupt (working, asking, delegating, booting, or an exited agent whose harness is mid-task), when the agent has background commands a restart may stop, or when another window shows it (`⇄`), since that window disconnects. An idle agent with no commands that nothing else shows restarts at once. Refused for the TUI's own session, an entry with no session, and a session `agent` didn't start (no record) |
| `R` | restart every agent the same way. An agent the restart would interrupt or whose commands it may stop is listed as busy. It always confirms, and skips the TUI's own session. An exited agent whose harness still runs has it stopped and stays exited |
| `x` | actions overlay ("Run on <agent>"): the configured actions, one key each. `Esc` closes. After an action the TUI rechecks other windows shortly after, so a window the action opened pauses the pane promptly. |
| `?` | keybindings (see Help) |
| `q` | quit |

## Choosing keys

The leave key and the agent chords are user config, and no terminal's key is the default's guarantee, so `agent keys` is how any user on any terminal picks one that works on theirs. It runs on a terminal only (`agent keys --explain <spec>` runs anywhere) in raw mode with no alternate screen, detects the keyboard the way the TUI does, pushes the same kitty flags and says which it found. A digit picks the field, and the next key press is the one tested. Each press prints its bytes, the event the TUI would see, and one verdict: usable, collides, ambiguous (the bytes are Tab's, Enter's, Esc's or Backspace's), composed (Option typed a character instead of acting as Alt) or unusable (no spec names it or the TUI wouldn't match it). A key counts only if some spec spelled on its character is one `Sendable::pressed` matches for that event in the detected mode, so the verdict can't disagree with the TUI. Kitty-only keys are usable with a note that a terminal without the protocol falls back to the default.

Collisions are data, a small table of keys readline, the terminal driver, zellij and agents commonly use, each weighted common or rare and all marked `from memory, unchecked`. A key with only rare claims is usable and lists them. A key with a common claim collides, and still prints the line to paste for a user who wants it anyway. The defaults must not read as warnings: the claim on `alt-.` says the default `next_agent` takes it on purpose. The probe never writes the config, and a line the config parser would refuse is replaced by its error.

The bytes are read from stdin and fed to a port of crossterm's parser, one byte at a time as crossterm does, because crossterm keeps the bytes behind its events and its parser isn't public. A test runs crossterm's own parser in a pty on the same bytes (C0 keys, Alt, function keys in the legacy and kitty forms, arrows with modifiers, CSI u with a shifted alternate, functional codes, reads split in the middle of a sequence) and requires the same events. What the port doesn't read (the Linux console's `ESC [ [ A`, keypad and media codes, Hyper and Meta) is a key with no event and is unusable. A lone Esc waits 25 ms for the rest of its sequence, where crossterm answers at once, so a key split across reads by ssh or a multiplexer is still one key.

The first time the TUI starts with no `[keys]` table, the status bar says where to change the keys, spelled from the same chords as the footer, and a job records that in the state directory. The marker is read at startup with the other state, so the UI thread never writes. The hint is never shown when the config has a `[keys]` table.

## Help

`?` opens a lazygit-style keybindings list: a rounded box titled `Keybindings` with `(type to filter)` on the right and `n of m` in the bottom-right corner. Rows are `key  description`, in a `Local` section (the focused panel's own keys, named beside the title) and then `Global`. The row under the cursor is reversed, and below the list a `Description` box gives the longer text for it. `↓`/`↑`, `j`/`k`, `⌃N`/`⌃P`, `Tab`/`⇧Tab`, `PgDn`/`PgUp`, `Home`/`End` move. Typing filters case-insensitively across the keys and descriptions, `Backspace` edits the filter, and `⏎` keeps the filter and returns to moving (`j` and `k` move again, and `/` edits the filter). While typing, `Esc` clears the filter and stops typing. Otherwise `?`, `q` and `Esc` close. The Description box's border names these. `j`, `k`, `q` and `?` are letters from the first other character or `/` typed until `⏎`. The list scrolls when it doesn't fit (it works at 80x24). Bindings that don't apply in the focused context aren't listed rather than struck through, which keeps the list short enough to scan at 80x24.

## Overlays

- **Switcher**: input focused on open. Index 0 is the previous agent, then pins, then MRU, then the rest. It never lists the TUI's own session. Rows use the Overview grammar: a main checkout reads `repo branch` (branch DIM) with nothing on the right. Other agents show their repo on the right (DIM). Age arrives with status. `⌃N`/`⌃P`/the nav key move, `⏎` selects the pick and previews it in NAV, and `Esc` returns unchanged. Rows: glyph, `agent`, repo DIM, age DIM. Matched characters BOLD Cyan. Rounded DIM border, BOLD title, hints in the bottom border.
- **Repo picker** (`p`): the same list grammar as the switcher. Rows are the sidebar's repos first, then the catalogue's repos the sidebar doesn't show, each group with an exact name first, then prefixes, then the rest. Every row ends with where the repo is (DIM, as `~/repos`), since a name alone can't tell two clones apart, and a listed row puts its live count before that (`● 2  ~/code`, default fg like the sidebar's counts). Text that starts like a path (`/`, `~`, `~/`, `.`, `./`, `../`) is the one row: the path keeping its end, and `add its repo` DIM. Whether it is one is checked off the UI thread when picked, and a failure lands in the status bar. With no row, the one row says `no match` (DIM) or `~user paths aren't supported` (Red) and the border offers only `Esc close`. Otherwise the bottom hint says what `⏎` does with the row under the cursor: `focus` a listed repo, `add` anything else. Adding lists the repo and focuses it once the next refresh shows it, unless a launch is already being followed. While the switcher or the picker is open the footer carries only `? keys`, since the border has the keys.
- **Check out** (`c`): the new-agent form (`Check out for review`) with its first field `branch` taking a branch name or a GitHub pull request link, and no `⌃E` or `⌃J`. The name is suggested from the branch (its words, lowercased, cut at the last whole word that fits) or the link (`pr-482`). It's never asked of the model and never made unique, since the branch decides: a branch already checked out in an agent worktree shows that agent in [0] whatever the form says. Submitting the form never enters AGENT. A link's problem shows under the branch field as it's pasted, a branch's only on `⏎`, since a branch is invalid mid-word. A pull request link also names its repo: with nothing typed in the repo field, the one listed or catalogued repo of that name is used, and otherwise the right of the repo row says `the link is acme/api` in Yellow. A branch git doesn't know is fetched from origin first, and a local branch of that name wins without a fetch. A pull request is asked of `gh`: from the repo itself it's checked out as its branch, so the agent can push to it, and from a fork its head is fetched by the `refs/pull/N/head` ref onto a `pr/N` branch tracking nothing, since origin has no branch of its own for it. A name that is an agent in another repo, or on another branch, is refused under the name before anything runs, in Red. All of it runs off the UI thread. Worker errors wrap under the name rather than being cut. The agent starts with no prompt.
- **Confirm**: sized to its content, with two short lines and hints in the bottom border padded by one space each side, the confirming key first and always BOLD Red (it must differ from the border), alternatives after it (`── Y discard and remove  k kill only  n/Esc cancel ─╯`). Border Yellow, Red when data would be lost, and the destructive key BOLD Red. Unmerged work lists the commit count per branch.
- **Restart** (`r`): while the plan is made, a one-line box titled `Restart <name>` (`Restart every agent` for `R`) saying `checking what would be interrupted…`. Confirmation, Yellow border, titled `Restart <name>?`: the state with its card glyph (`◆ asking`, the spinner and `working` or `booting`, `↳ delegating`, the spinner and `working in the background` for a harness process mid-task), `The activity stops. The conversation resumes.`, and for an agent another window shows `⇄ in nvim · its window disconnects` in Yellow. One line per background command follows, in Yellow, as `may stop ⌁ cargo test --workspace · 4m+` (the name as the cards show it, the time it has run at least with the `+`, a name cut to 40 columns), up to three, then `… and 2 more`. A command that prints nothing once cleaned has no line but is counted: `… and 1 more` after the named ones, or `may stop ⌁ 2 background commands` when none can be named. An idle agent with commands is asked, and reads `Restarts <harness>. The conversation resumes.` above them. A restart confirmed here stops nothing the box didn't show: if the agent starts working, or runs a command the box didn't list, before the restart runs, it is skipped (`skipped x: started working`, `skipped x: started running 1 background command: npm run dev`, naming only the commands it wasn't shown). An agent that is neither busy, running commands nor shown elsewhere isn't asked. One that is only shown elsewhere reads `Restarts <harness>. The conversation resumes.` above the window line. Keys `y/⏎ restart` with the key BOLD Red like any confirming key, and `n/Esc cancel`.
- **Restart all** (`R`): titled with what it would do, `Restart 5 · stop 2 exited · 3 busy`, each part left out when it's zero (so `Stop 2 exited` when nothing else is). Busy agents are listed one per row with their card glyph and state (up to five, then `+n more busy`), and an agent that is only running commands reads `⌁ running 2 background commands` (an exited one `running 1 background command, stays exited`), an exited agent whose harness is mid-task reads `<harness> working, stays exited`. Then one summary line: `3 idle`, `2 exited stop their <harness>`, `1 open in other windows, which disconnect`, `this TUI's session stays`, `n can't be checked`, then `Busy ones stop mid-activity. Conversations resume.`, `Busy ones may stop their commands. Conversations resume.` when they only run commands, or `Busy ones stop mid-activity and may stop their commands. Conversations resume.` when some do each. Keys `y restart N` (BOLD Red), `i idle only (M)` when any is busy, `n/Esc cancel`. `⏎` confirms too.
- **Restart progress**: a restart is a message to one restart thread, which runs them in order and answers each. A card reads `restarting` (the spinner) from the moment `y` is pressed until its answer, and `⏎` on it says `<name> is restarting`. The status bar says `restarting <name>…` or `restarting 3 of 7…` while any are pending, then `restarted <name>`, `restarted 5 · 2 failed · api-auth: … · web: …` (an error, kept until a key) or `skipped x: started working` for an agent that became busy after it was approved idle. A restarted agent that is selected is previewed in NAV once the refresh shows its session. Quitting asks when restarts are still queued, and the one in flight finishes.
- **Help**: the full keymap. Section headers are the same reversed-Cyan badges as the footer (`AGENT`, `NAV`). Keys and descriptions in default fg (DIM is unreadable on some themes at this density). Sized to fit 80x24, in two columns when the terminal is short.

## Empty and transient states

One centred line in the terminal area, verb first, never a second hint block (the footer already has the keys): `⏎ resurrect tanda_cli`, `⏎ start claude here` (key BOLD), `attaching to fix…`, `this TUI runs here` (DIM), `No agents yet` (DIM). A worktree whose name is over the session host's limit is still listed and removable, and its line says why it can't start (Red), for example `'an-over-the-limit-worktree' is 7 bytes over the session host's limit of 20`. `⏎` on it shows the same as a status error and starts nothing.

## Truncation

Names keep their start (`payroll-fix-for-ti…`), paths keep their end (`…/heucristic/triage-flow`), measured in display width. Right-aligned metadata never truncates, so names yield first.
